Bonus Lesson B

Sounds

Add the click, the ding, and the music. It changes everything.

TimingOne period (~50 min), plus library install time if it is not already done
New ideaPlaying audio on game events
Builds onLesson 7 — collisions, so there is an event worth putting a sound on.
StandardInstall the Sound library, load a SoundFile from data/, play one-shot effects on game events, and loop background music.

Warm-up (~5 min)

What sounds do your favorite games use? Background music? Sound effects? Pick one sound and say what it tells the player.

Direct instruction (~10 min)

Install the library BEFORE class if at all possible

Sketch → Import Library → Add Library, search "Sound", select Sound by The Processing Foundation, install, restart Processing.

Doing this live with a full class costs ten to fifteen minutes and a certain number of failures. If you can push it to the machines ahead of time, do.

The import line is import processing.sound.*; — a second import alongside the sprites one.

Sound files in data/

Same data/ folder as images: Sketch → Show Sketch Folder, drag files in.

MP3, WAV, OGG, AIFF are supported. WAV is the most reliable; MP3 works but occasionally misbehaves on some systems.

Royalty-free sources: freesound.org (free account required to download), opengameart.org, zapsplat.com.

Loading and playing

Declare at the top: SoundFile collectSound;

Load in setup(): collectSound = new SoundFile(this, "collect.wav");

Play on the event: collectSound.play();

Background music: bgMusic.loop(); once in setup() and it runs forever.

Where to trigger — this is the actual lesson

The one-line API is trivial. The thinking is about placement, and that is what the wrap-up question is about.

On collision: inside the if (player.collidesWith(...)) block. On game over: exactly where gameOver is set to true. Music: once in setup().

Frame it as: "a sound goes where the *event* happens." That connects straight back to the continuous-versus-event idea from Lesson 4.

play() versus loop()

.play() starts the sound once; calling it again while it is playing restarts it from the beginning.

.loop() keeps going forever until .stop().

For collision effects, .play() is perfect. For music, .loop() is what you want. Say both out loud — students reach for .loop() on effects and then cannot work out why it will not stop.

Guided activity (~20 min)

  1. Verify the Sound library is installed on every machine, or install it as a class. Budget real time for this.
  2. Each student finds two files: a short effect (WAV strongly preferred) and optionally a ~30-second music loop.
  3. Everyone drops them into data/ and reads their filenames out loud, exactly.
  4. Add the import, the declaration, and the setup() load together. Run — nothing audible yet, because nothing calls .play(). Name that.
  5. Add collectSound.play() inside the collision if. Run. Collect something. The room will react.
  6. Debug null pointers as a group. It is always the filename or the folder.
  7. Add music with .loop(), then immediately add .amp(0.3) when the room gets too loud — which it will, and that is a good live demonstration of why volume balance matters.
  8. Release for personalization: hazard sounds, milestone sounds, key-press sounds.

Common mistakes to watch for

  • Library not installed, or Processing not restarted after installing. import processing.sound.*; fails to resolve.
  • NullPointerException on a SoundFile — this always means the file was not found. Check the data/ folder and the exact filename first, every time.
  • Filename typos, including extension and capitalisation.
  • .loop() used for a collision sound — it never stops and the student cannot work out why.
  • .play() called every frame because it was put in draw() instead of inside the if. Machine-gun stutter. A great teachable moment about event versus continuous.
  • Music at full volume drowning out effects. amp(0.3) fixes it.
  • Zipping the sketch without data/ at submission time, so no sounds ship.
  • Very long MP3s (a full 4-minute song) bloat the sketch folder. Ask for short loops.

Wrap-up (~5 min)

Ask: Where in your game did you put the sound call, and why there and not somewhere else?

Looking for: Inside the if block that detects the event — because that is the exact moment the thing happens, and it only runs then. Students who put it in draw() will have heard the machine-gun effect and will explain it well.

Teaching notes

  • Sourcing sounds can absorb the entire period. Having a small pre-vetted folder of effects ready is worth the prep.
  • This is enrichment. Nothing in the capstone needs it, but it is the single change that most makes a student's game feel *finished*.
  • The placement question — *where* does the sound call go — is the transferable idea. The API is three methods.
  • Fast finishers: guarded playback with isPlaying(), milestone sounds, or a sound tied to a key press.
  • Headphones, if you have them, will preserve your sanity during work time.
  • Pairs naturally with Bonus Lesson A as a two-part "make it real" session, since both use the data/ folder.
