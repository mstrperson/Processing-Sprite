Lesson 6

If This, Then That

Your program starts making decisions instead of just following orders.

TimingOne period (~50 min)
New ideaif statements and variables that change
Builds onLesson 5 — your world full of objects.
StandardUse if, changing variables (int score), and text() to make the program react and track state.

Warm-up (~5 min)

How did you add 12 coins to your world last time? Which loop did you use, and where did it go?

Direct instruction (~10 min)

Global scope — say why, not just where

int score = 0; and boolean gameOver = false; go above setup(). "These live outside setup() and draw() so all functions can see them."

Students will try to declare them inside setup(). When they do, the variable disappears the instant setup() ends. Show that failure once if you have time — the error message is not obvious.

The if statement

"The condition in the parentheses is either true or false. The code inside the braces runs only when it is true."

Demo something loud and visible: if (score > 10) { background(255, 0, 0); } and then set the score by hand to show both branches.

= versus ==

Worth thirty explicit seconds. A single = assigns; a double == asks. Write both on the board.

In Java the compiler will usually catch if (score = 10), which is a mercy, but they need the vocabulary to read the error.

Displaying text

fill(0); textSize(24); text("Score: " + score, 20, 36);

"The + here glues text and a number together into one string." Do not use the word *concatenation*.

Point out that fill() has to come before text(), or the text inherits whatever color the last shape used. This will bite someone.

The boolean state variable

if (!gameOver) { ...play... } else { ...show game over... }

"! means NOT — so if not gameOver means if the game is still going."

This is the structural idea of the lesson. The game has modes, a variable remembers which one, and draw() picks. Everything in Lessons 7 and 9 builds on this shape.

Build it up in stages, not all at once

Variable declared → changed in draw() → displayed on screen → used in an if to branch. Four separate runs.

Pasting the whole finished structure at once hides where each piece came from.

Guided activity (~20 min)

  1. Add the two global variables at the top together. Run — nothing changes yet.
  2. Add the text() call so the score shows. Run. Now there is something on screen to react to.
  3. Test by cheating: change int score = 0; to int score = 7; and run. The display updates. Set it back. Testing a display by hand-setting the value is a real technique and worth naming.
  4. Refactor together: move the game body from draw() into playGame(). Run — nothing should change. Emphasise that: a refactor that changes nothing visible is a *success*.
  5. Add the if/else in draw() and write showGameOver(). Run — still plays normally.
  6. Test the other branch by cheating: set gameOver = true in the declaration and run. Straight to the game over screen. Set it back.
  7. Add the real trigger (if (score >= 10)). Release for personalization.

Common mistakes to watch for

  • Declaring globals inside setup(). Scope error. The most common structural mistake in this lesson.
  • = instead of == in a condition.
  • fill() after text() — text comes out in an unexpected color.
  • textAlign(CENTER, CENTER) never reset. It affects every later text() call, so the score display in the corner silently moves. The starter resets it with textAlign(LEFT, TOP) at the end of showGameOver() — make sure students who restyle that function keep the reset.
  • Nothing ever changes score, so the if can never fire. Note out loud that coins are drawn but not yet collectable — that is Lesson 7. Some students will find this unsatisfying; tell them the payoff is next lesson.
  • Forgetting the braces on a one-line if and then adding a second line later that runs unconditionally.

Wrap-up (~5 min)

Ask: What is the difference between an int and a boolean? Give an example of each from your own game.

Looking for: int holds a whole number (score, lives, level). boolean holds only true or false (gameOver, paused). Look for an example from their own sketch, not a generic one.

Teaching notes

  • score++ is shorthand for score = score + 1. Fine to mention if a student asks, but keep score = score + 1 in the starter so the operation stays explicit.
  • Coins are drawn but not collected yet. Say this up front so students do not spend the period hunting for a bug that is not there.
  • The "test by cheating" move — hand-setting a variable to check a branch — is a genuine debugging skill. Name it while you use it.
  • Only one new concept today: if. Variables and text() are the supporting cast. If a student is struggling, drop the playGame() refactor and just get an if working in draw().
  • Fast finishers: layered conditions, or a lives counter. Both are extensions of the same idea rather than new ones.

Rubric reference (no points)

Standard
Use if, changing variables (int score), and text() to make the program react and track state.
Getting StartedMy score or text will not show, or my if never triggers. Next step: declare your variables at the top (outside setup and draw) so every function can see them, and double-check your if condition.
Got It WorkingA variable changes during play, shows on screen with text(), and an if branches the game (playing vs. game over).
Made It Mine ⭐…and I changed what triggers the state change (a time limit, a different score), restyled the game-over screen, or added a second variable like lives.
Went Beyond…and I combined multiple conditions or variables so the game reacts in layered ways — the background shifts as score rises, lives count down, and so on.

⭐ Made It Mine is the goal for everyone. “Went Beyond” has no fixed list — the examples are only starting points. Going somewhere the lesson did not ask for is the whole idea.
