Lesson 4

You're in Control

Your character stops doing its own thing and starts doing what you tell it.

TimingOne period (~50 min)
New ideaInput — the program reacting to you
Builds onLesson 3 — setVelocity() and move().
StandardControl the character with followMouse() or keyboardControl(), and distinguish continuous input from event input.

Warm-up (~5 min)

What does move() do, and where does it go? What happens if you leave it out?

Direct instruction (~10 min)

followMouse() — and the speed requirement

It goes inside draw() and runs every frame, pulling the character toward the cursor.

It uses vel.mag() as the chase speed. If the velocity is (0, 0), followMouse() moves the character exactly zero pixels and looks completely broken. Call player.setVelocity(4, 0) in setup().

Also: when using followMouse(), do not call move(). followMouse() writes the position directly, and calling both makes the motion fight itself.

keyboardControl() — and where it goes

It goes inside keyPressed(). Not draw().

In draw() it does nothing useful, because keyCode is 0 on the ~59 frames out of 60 where no key went down. The failure is silent, which makes it a nasty bug for a beginner to find.

After keyPressed() sets the velocity, move() in draw() applies it each frame. So the draw() loop still looks exactly like Lesson 3.

The continuous vs. event distinction

This is the transferable idea in the lesson, and it is worth more than either method.

"Where is the mouse?" always has an answer, so you can ask every frame. "Did the player just press a key?" only has an answer at one instant, so the system has to come tell you.

Frame it as a question they could answer about any program, not a rule about these two functions.

Demo the switch live

Put followMouse() in draw() and run — instant, obvious. Then comment it out, uncomment move(), add keyPressed(), and run again.

Doing both on the projector in ninety seconds makes the choice concrete before you ask them to pick one.

The coasting conversation

With keyboardControl(), releasing the key leaves the velocity unchanged, so the character coasts. Students expect it to stop.

This is a genuinely good discussion about state: the character is not "being pushed," it *has* a velocity, and nothing has changed it back. Nobody told it to stop.

If they want it to stop, keyReleased() with setVelocity(0, 0) does it. Offer it only if they ask.

Guided activity (~20 min)

  1. Everyone opens Lesson 3's sketch. Confirm setVelocity() is in setup().
  2. Swap move() for followMouse() together. Run. Everyone chases the cursor for a minute — let them play, it is fun and it costs nothing.
  3. As a class, change the speed to 1, then to 12. Ask which feels better and why. There is no right answer; the point is that they have an opinion.
  4. Switch to Option B together: comment out followMouse(), restore move(), add keyPressed() at the bottom.
  5. Remind everyone to click inside the sketch window before using the keyboard. This will strand people otherwise.
  6. Have everyone press an arrow and release. Ask what happened. Run the coasting discussion here.
  7. Students choose their control style and tune it. Circulate.

Common mistakes to watch for

  • followMouse() with no velocity set. Moves zero pixels. Looks broken, is not. Check setup() first every time.
  • Calling both followMouse() and move(). The motion fights itself and looks jittery.
  • keyboardControl() inside draw(). Silent failure — nothing happens and there is no error message.
  • Window not focused. Keyboard input goes nowhere until they click inside the sketch window. Costs students five minutes each if you do not warn them.
  • Deleting move() when switching to keyboard control. The velocity gets set and then never applied.
  • Expecting the character to stop on key release. It coasts. This is state, not a bug.

Wrap-up (~5 min)

Ask: Why can't you put keyboardControl() inside draw() instead of keyPressed()?

Looking for: draw() runs ~60 times a second whether or not a key was pressed, so there is usually nothing to read — keyPressed() fires only at the instant a key actually goes down. Accept anything that captures "draw runs all the time, keyPressed only when it happens."

Teaching notes

  • Have students try both styles before choosing. The choice is more meaningful if they have felt the alternative, and it is their first real design decision in the unit.
  • followMouse() is easier and more forgiving; keyboardControl() feels more like a real game. Both are fine choices for Lesson 9.
  • Fast finishers: keyReleased() with setVelocity(0, 0), or a mousePressed() ability. Both are one-liners with a big feel change.
  • Whatever they choose today, they can change later. Say that out loud so nobody agonizes.

Rubric reference (no points)

Standard
Control the character with followMouse() or keyboardControl(), and distinguish continuous input from event input.
Getting StartedMy character does not respond to input yet. Next step: for followMouse, set a speed with setVelocity() in setup() — it needs a speed above 0 to move at all. For keys, make sure keyboardControl() is inside keyPressed(), not draw(), and that you clicked inside the sketch window first.
Got It WorkingI can drive my character with the mouse or the arrow keys.
Made It Mine ⭐…and I picked the control style that fits my game and tuned it — a speed that feels right, or a mousePressed() that does something fun.
Went Beyond…and I combined inputs (keyboard control plus a mousePressed() ability), or added a second blob that moves on its own while I steer the player.

⭐ Made It Mine is the goal for everyone. “Went Beyond” has no fixed list — the examples are only starting points. Going somewhere the lesson did not ask for is the whole idea.
